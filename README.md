
## Запуск

```bash
pip install pandas pyarrow numpy scipy scikit-learn snowballstemmer torch
DATA_DIR=<папка с parquet-файлами> bash run.sh        # → answer.csv (~20 мин на 2 ядрах CPU)
DATA_DIR=<папка с parquet-файлами> bash run.sh val    # + валидация и проверка весов (ещё ~40 мин)
```

| Файл           | Что делает                                                       |
| -------------- | ---------------------------------------------------------------- |
| `common.py`    | Пути, веса, нормализация и стемминг текста, чтение данных        |
| `prepare.py`   | Подготовка таблиц для теста (`test`) и валидации (`val`)         |
| `dssm.py`      | Обучение нейросети bi-encoder и расчёт эмбеддингов корпуса       |
| `retriever.py` | Расчёт сигналов релевантности и итогового скора по всему корпусу |
| `predict.py`   | Top-50 для запросов benchmark, проверка формата, `answer.csv`    |
| `validate.py`  | Сборка валидационного корпуса, замер Recall@50, подбор весов     |

## Что сделано, по шагам

### 1. Анализ данных 

- **Гео — сильнейший сигнал.** Если поиск шёл по городу, пользователь в 93% случаев выбирает объявление из того же города.
- **Локация поиска бывает регионом.** У 17% запросов benchmark локация — регион, в котором нет ни одного объявления. Поэтому нельзя требовать равенства id локаций: нужна вероятность того, что объявление окажется в данной локации.
- **Запросы в основном новые.** Только 37.5% текстов запросов benchmark встречаются в train.
- **По id объявлений train почти не пересекается с корпусом.** Только 9.6% объявлений корпуса есть в train. Зато у 49% совпадает заголовок с каким-то объявлением из train, поэтому историю выборов удобно привязывать к заголовку.
- **Корпус «сгущён» вокруг запросов benchmark.** У каждого запроса десятки похожих объявлений из того же города и подкатегории. Это сделало задачу труднее, чем казалось на первой валидации.

### 2. Обработка текста

- **Нормализация.** Нижний регистр, «ё» → «е», удаляем знаки препинания.
- **Стемминг** (Snowball для русского языка). Слово обрезается до основы: «телевизоров» → «телевизор». Так разные формы одного слова совпадают.
- **Биграммы.** Кроме отдельных слов используем пары соседних слов («баня_дров»). Они ловят устойчивые словосочетания.
- **Экономия памяти.** Описания объявлений обрезаются до 700 символов (300 для нейросети) и читаются из parquet потоково.

### 3. Сигналы релевантности (`retriever.py`)

Для каждой пары «запрос — объявление» считаются шесть сигналов.

1. **`s_full` — текстовое сходство.**
   - *TF-IDF* превращает текст в вектор весов слов. Вес слова растёт, если оно часто встречается в этом тексте, и падает, если встречается во многих объявлениях (IDF, обратная документная частота). Так редкие, «говорящие» слова весят больше. Используем сублинейный TF: 1 + log(частота), чтобы десятое повторение слова почти ничего не добавляло.
   - *Косинусное сходство* — косинус угла между векторами запроса и объявления: 1, если тексты совпадают по составу слов, и 0, если общих слов нет.
   - Текст объявления = заголовок ×2 + параметры + описание. Заголовок повторён дважды, чтобы весил больше.
2. **`s_desc` — сходство запроса только с описанием** объявления.
3. **`s_params` — сходство «запрос + фильтры поиска» с параметрами объявления.** Например, фильтр «Вид услуги Красота, здоровье» совпадает с параметром объявления.
4. **`s_mem` — логовая память** (идея doc2query). К объявлению приписываются запросы из train, по которым выбирали объявления с таким же заголовком. После этого объявление «знает», какими словами его ищут пользователи.
5. **`loc_lp` — гео-приор**, log P(локация объявления | локация поиска).
6. **`s_dense` — нейросеть bi-encoder (`dssm.py`).**
   - *Bi-encoder* — две «башни»: одна превращает запрос в вектор, другая — объявление. Сходство — косинус векторов. Такая модель понимает близость текстов без общих слов («обзвон по базе» ≈ «холодные звонки»).
   - *Hashing trick*: слова, их пары и символьные 3-граммы («#те», «тел», …) хешируются в 262 тыс. ячеек таблицы эмбеддингов, и словарь хранить не нужно. Символьные 3-граммы дают устойчивость к опечаткам.
   - *Обучение с нуля* на 497 тыс. пар «запрос — выбранное объявление» из train, 3 эпохи на CPU (~9 мин). Готовые предобученные модели скачать было нельзя: в среде разработки нет доступа к HuggingFace.
   - *InfoNCE с in-batch негативами* — функция потерь, которая для каждого запроса в батче из 1024 пар учит свой объявление отличать от 1023 чужих. Чужие объявления из того же батча служат бесплатными отрицательными примерами (*негативами*). Мягкость сравнения задаёт *температура τ*, она тоже обучается.

### 4. Итоговый скор и выбор кандидатов

`score = 2.66·s_full + 0.40·s_params + 0.53·s_desc + 0.05·s_mem + 0.15·loc_lp + 1.33·s_dense`

- Скор считается для **всех** объявлений корпуса. Для каждого запроса берутся 50 объявлений с наибольшим скором.
- Такой выбор оптимален для Recall@50: если скор монотонно связан с вероятностью выбора, то top-50 по вероятности даёт максимальное ожидаемое значение метрики.
- Веса подобраны *координатным спуском*: по очереди меняем один вес (×0, ×0.5, ×0.75, ×1.33, ×2) и оставляем изменение, если Recall@50 на валидационной выборке A вырос. Проверка — на отдельной выборке B.

### 5. Эксперименты

| Вариант                                                          | Валидация | Лидерборд |
| ---------------------------------------------------------------- | --------- | --------- |
| Только текст (TF-IDF), без гео                                   | 0.30      | 0.32      |
| Текст + гео-приор                                                | 0.79      | —         |
| Линейный скор, веса «на глаз»                                    | 0.88      | 0.83      |
| + двухэтапная схема с ранкером LightGBM (обучен на валидации v1) | 0.95 (v1) | 0.67      |
| + ранкер LightGBM без «утекающих» признаков (валидация v3)       | 0.90      | 0.83      |
| **Линейный скор, подобранные веса (финал)**                      | **0.89**  | **0.86**  |

- **Ранкер** — вторая модель, которая переупорядочивает ~1100 кандидатов первого этапа. Использовался *GBDT* (градиентный бустинг решающих деревьев, библиотека LightGBM).
- **Почему ранкер провалился.** На валидации v1 у него была *утечка*: признак «объявление выбирали в train» почти идеально указывал на правильный ответ, потому что позитивы брались из train, а соперники — нет. В тесте этот признак ничего не значит.
- **Как это нашли.** Помогла *adversarial validation*: модель учится отличать строки валидации от строк теста. AUC 0.99 означал, что распределения признаков сильно различаются. AUC (площадь под ROC-кривой) равен 0.5, если различить нельзя, и 1.0, если можно идеально.
- **Ранкер и после исправления проигрывает линейному скору.** Даже без утечки он дал на лидерборде 0.83 против 0.86. Поэтому финальное решение — одна линейная формула: она проще и лучше переносится на тест.
- **Не дали прироста на валидации:**
  - символьные n-граммы заголовка;
  - kNN-приор подкатегории по похожим train-запросам;
  - гео-вес, зависящий от подкатегории;
  - отдельный вес для региональных запросов;
  - 6 эпох обучения нейросети вместо 3;
  - компактный ранкер поверх линейного скора (+0.3 пункта — слишком мало при риске сдвига).
